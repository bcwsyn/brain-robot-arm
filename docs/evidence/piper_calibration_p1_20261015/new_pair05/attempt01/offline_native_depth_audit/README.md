另外固定一个8480像素的外围控制环，只作背景稳定性对照，不当桌面平面或方块测量。后两批有效占比约69%–73%；与首帧共同有效像素的绝对深度差中位数每帧为0或1mm。与关节/内参一致性合起来，证据指向局部目标区域的原始深度失效，而非整幅深度缩放、模型坐标跳变或机械臂继续运动。

## 仍不能断言的事

- 三批之间相机流被分别关闭再启动；变化与重开流相伴，但未做受控实验，不能据此断言“重开一定造成问题”，也不能归罪物体被用户移动。
- 原始深度0可以定位数据失效层，不能仅由本数据区分材质、观察条件、设备内部处理、驱动状态等物理/软件根因。
- 没有记录原生深度逐帧曝光、红外强度、投射器状态或置信度。RGB自动曝光元数据不能代替它们。
- 当前源代码中`ir is not enable`来自未启用IR图像流的分支，不是投射器关闭的证据。没有调用laser/LDP setter，也没有理由解除激光保护。
- 即使首批3帧存在完整方形面，它们仍未满足原桌面/顶面判断，而且少于20帧；本分析不把它们升级为合格A。原A60/0、完整合格1/6、四位置有原始A+B都不变。

## 当前代码核对（只读，不作为设备实测）

已核对当前部署工作区及规范仓库对应源码，哈希和行号见verification.json。安装的相机运行库来源由旧启动日志记录，本轮没有验证二进制与当前源码的构建同一性：

- `collect_static_rgbd.py:157`深度用CvBridge passthrough编码无损PNG，未做颜色掩膜、补洞或目标区置0。
- `ob_camera_node.cpp:446`的深度发布回调读取OpenNI帧，按depth_scale做最近邻尺寸处理并发布；当前配置depth_scale=1、depth_align=false。这里没有按紫色目标框置0的代码。源代码检查不能证明设备内部从未处理数据。
- `ros_service.cpp:26`仅为启用的流创建控制服务。当前深度流可对应`get_depth_exposure/get_depth_gain`，IR图像流关闭不等于没有深度曝光接口。
- `ros_service.cpp:341`及183的深度曝光/增益读取分支忽略底层getProperty返回状态，因此将来即使getter回复success=true且data=0，也不能冒称0已被可靠测得。
- `set_laser_enable/set_ldp_enable`均是会写设备/重启流的setter，不属于下一步只读检查，未调用。
