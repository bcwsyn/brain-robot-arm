# PiPER 固件线索与夹爪恢复实验（2026-10-12）

## 实际状态

- 起点 HEAD：`0e14678`。
- 无 ROS、视觉、适配器或一键进程；`can0` 为 UP/LOWER_UP、1 Mbps、ERROR-ACTIVE，读数错误、丢包、仲裁丢失为 0。
- 用户补充的现场时间线：一次固件升级后机械臂整体无法驱动；下一次升级恢复六轴；夹爪尚未验证。
- 仓库固件资料：上位机 `ArmRobotUA 1.6.3.260828`，合并固件 `MC(S-V1.9-1)_DRV(V2.0.8)`。没有现场两次升级的独立安装日志。

## 有界动作

1. 使用 root 环境执行脚本时，首次因缺少用户级 `piper_sdk` 路径在导入阶段退出；显式设置 `PYTHONPATH=/home/johnwick/.local/lib/python3.10/site-packages` 后才实际执行。
2. 读取状态后发送一次 `EmergencyStop(0x02)`，等待，再发送 `EnableArm(7)` 三次、`MotionCtrl_2(0x01,0x01,50,0)`、夹爪 `0x02→0x01` 握手和一次 50000（50 mm）目标。没有 `JointCtrl`、没有六轴目标、没有 `ResetPiper`。
3. SDK 输出：动作前后夹爪均 `angle=0/status=0`；没有 SDK 角度变化。动作后低速六轴状态暂为失能。
4. 立即执行仅包含 `EnableArm(7)` 三次的恢复动作；被动采样显示 `0x261..0x266` 末字节均恢复 `0x40`，没有夹爪或关节目标。
5. 之后只读 `candump` 4 秒收到 800 个 `0x3A7`，位置始终 `98200`、状态始终 `0`；六轴高速帧各约 400、低速帧各约 80，CAN 错误/丢包仍为 0。

## 结论与阻断

- `EmergencyStop(0x02)` 不是本机夹爪恢复手段，禁止重复试探。
- 原始 `0x3A7` 与 SDK 缓存当前不一致，SDK 的 `angle=0` 不能替代原始 CAN 位置证据。
- 夹爪普通使能/目标、SDK CPV 和急停恢复均未产生 `status=0x40` 或可证明的机械位移。结合用户固件升级时间线，固件与夹爪驱动兼容性是最高优先级假设，但还没有固件版本读回或官方支持确认能够单独证明它。
- 官方 issue #128 的厂商处理意见是用最新版 ArmRobotUA 完成 CPV 复位，再重新闭合并设置零点；Linux 端没有该 Windows 上位机的可执行链。本轮不模拟刷写、不运行危险重置。
