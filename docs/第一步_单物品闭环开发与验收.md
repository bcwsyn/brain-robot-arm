# 第一步：单物品取放闭环开发与验收

日期：2026-10-12。对应[原验证报告的第一步](小球与圆柱体仿真验证及下一步规划.md#第一步先得到一个可重复的单物品闭环)。范围为 `simulation/`；真实机器人工作区未参与构建或运行。

## 1. 这一步要解决什么

让一件小球或实心圆柱体完成：

```text
收到开始请求 → 观察 → 找到红色目标 → 居中
→ 暂停 Servo 并取得控制权 → 关节静止 → 打开夹爪
→ 保存目标 → 选择可行的斜侧抓 → 接近 → 闭合
→ 检查夹爪与物体的位置 → 跟随式抬升 → 搬运
→ 降到放置高度 → 停止跟随 → 打开夹爪
→ 向上退出 → 回到 zero 待机姿态 → COMPLETE
```

**这里的完成只表示跟随式取放流程。** 物品仍关闭重力，并由 Gazebo 插件设置位置。`flow_demo=true` 还明确关闭物品的 Gazebo 接触力响应，避免强制跟随与接触力相互冲突。MoveIt 中仍保留物体、桌面与机械臂的碰撞几何，仅允许夹爪组件接触目标。算法的位置检查不是触觉/力传感器反馈，不能据此声称物理抓取成功，更不能替代申请书的 88% 指标。

## 2. 已实现的改动

| 原问题 | 当前处理 | 主要位置 |
| --- | --- | --- |
| 加载缺库的 Pilz/CHOMP | 抓取相关启动文件明确只加载 OMPL；保留现有系统包，无版本冒充链接 | MoveIt 与视觉启动文件 |
| Servo 在抓取中重新启动 | 新增 `claim_grasp_control` 服务；抓取执行器领取/释放控制权；领取期间禁止视觉 jog、重新开始与重新捕获 | `visual_search_controller.cpp`、`grasp_lift_executor.cpp` |
| 预计算轨迹起点过时 | Servo 停止确认后等待位置样本稳定；下一段笛卡尔路径从新鲜实测关节状态重算；MoveIt 原有 0.01 rad 起点检查保留 | `grasp_lift_executor.cpp` |

| 圆柱体顶抓/翻转中丢目标 | 默认跳过原大角度 LEVEL_ALIGN；直接从视觉居中进入斜侧抓候选，先做 IK，再做碰撞规划和完整接近路径检查 | 两类物品的仿真任务配置 |
| 候选循环覆盖已找到的解 | 第一个预抓取和接近都可行的候选退出全部循环；拒绝单关节跨度 >1.2 rad 或接近耗时 >10 s 的解，并检查起点 ±0.001 rad 邻域 | `DiagonalSidePointGraspAndLift()` |
| 图像对应 TF 稍晚到达 | 长度最多 16 的等待队列；按图像时间戳查询 TF，过期样本淘汰；最多等待目标模型 5 s，无任意最新 TF 回退 | 执行器目标缓存 |
| 视觉无限恢复 | 一次开始请求最多 2 个搜索恢复周期；视觉任务总上限 180 s；抓取执行段上限 120 s | 视觉 FSM 与执行器 watchdog |
| 只抬起，没有取放 | 固定放置区中心 `(0.40, 0.12)` m；保持物品竖直方向并随底座方向转动搬运姿态；释放后退出和回零 | `FinishGraspAndLift()` |
| ready 含义混用 | 场景 ready 保留各场景前缀；执行器 ready 统一为 `/brain_robot_grasp/scene_ready` | 球任务配置 |
| MoveIt 物体位姿表示不同 | 合并 `CollisionObject.pose` 与 primitive pose，统一到物体 header 坐标系后再计算抓取/放置 | `PrepareScene()` |
| 控制器偶发启动失败 | 使用同一长驻节点依次加载、配置并激活 4 个仿真控制器；给 DDS 服务发现留出 2 s；验证程序先等控制器，再创建场景 | `sim_controller_bootstrap.py`、验证脚本 |

没有训练新模型。视觉仍是 HSV + 形态学 + RGB-D 几何；抓取采用已知球/圆柱体形状先验和有限姿态候选；规划采用现有 KDL IK、OMPL/RRTConnect 与笛卡尔路径。

视觉提供目标 x/y；默认桌面高度、已知物品尺寸/场景高度参与确定抓取高度。球还留出 18 mm 夹爪与桌面间隙。这只适用于当前已知形状、固定桌面的两类场景，不能直接推广到未知物品或未知桌面。

### 2.1 初学者怎么读这些改动

- **HSV/RGB-D**：先按红色找物品，再用深度图把像素位置换成空间位置。这里只识别当前红色目标，尚未做多类别识别。
- **逆运动学（KDL IK）**：输入“夹爪要到哪里、朝向哪里”，求出六个关节该转到什么角度。求不出解就换一个抓取方向。
- **OMPL/RRTConnect**：在能到达的关节角之间找一条避开碰撞的路，用于预抓取、搬运和回待机。
- **笛卡尔路径**：让夹爪沿空间中的短直线接近、抬升、下降和退出；实际执行前用当前关节状态重新计算。
- **状态机与控制权交接**：规定这一刻由谁控制机械臂，避免“视觉还在追目标，抓取又开始移动”。

## 3. 开发中发现并保留的失败

`simulation/validation/step1/` 保留开发对照和最终验收数据。失败没有从统计记录中删除，也没有改变原始来源归档。

- `ball-debug-01/02`：速度字段残留导致交接等待超时。
- `ball-debug-03`：较低抓取高度导致接近笛卡尔路径不完整。
- `ball-debug-04`：抬升成功，但固定朝向平移的搬运目标 IK 无解。
- `ball-debug-05`：夹爪闭合后物理接触力与跟随物体冲突，关节抖动。
- `ball-debug-06`、`cup-debug-01..04`、`acceptance-01`：控制器/DDS 启动失败，部分 Gazebo 原生服务因发送响应失败退出；这些不是成功的抓取试验。
- `acceptance-02`：小球 20 次通过、圆柱体 7 次通过后第 8 次在实测接近路径失败。该候选预检查时发生大幅腕部绕转、路径异常长；补充关节跨度/耗时与起点邻域筛选后，`cup-robust-01` 在失败位置连续 5 次通过。最终完整批次另存，不删除该失败。
- `ball-debug-07`、`cup-debug-05`、`cup-known-01`：开发期单轮完整取放通过。
- `negative-stop`：停止服务、停止状态和静止判断均满足，但按固定条数保存的反馈队列在高频发布下只覆盖约 0.5 s，未达到至少 1 s 的观测要求，故判为不通过；验证器改为保留最近 3 s 的全部样本，重新运行另存记录。
- `gazebo-rpc-debug`：带调试器的运行未复现通信异常；该轮是诊断对照，不能证明启动问题已解决。

针对通信异常，验证进程采用本地 UDP 配置和异步发布；随后增加长驻服务客户端与发现等待。UDP 单独使用时仍失败，因此没有把它写成已证实的唯一根因。配置只作用于这些进程，不修改系统网络或 `/etc`。参数用法参考 [Fast DDS UDP 文档](https://fast-dds.docs.eprosima.com/en/v2.6.11/fastdds/transport/udp/udp.html)和 [ROS 2 rmw_fastrtps 官方说明](https://github.com/ros2/rmw_fastrtps)。

## 4. 验收方式与结果

### 4.1 预先规定的试验

最初计划保存在 `simulation/validation/step1/trial_plan.json`。修复腕部绕转后使用 `trial_plan_final.json`，保留相同位置与次数，先测曾失败的圆柱体位置，两个计划均在对应整组执行前保存：

| 位置 | x（m） | y（m） | 小球次数 | 圆柱体次数 |
| --- | --- | --- | --- | --- |
| P1 | 0.38 | -0.12 | 5 | 5 |
| P2 | 0.40 | -0.12 | 5 | 5 |
| P3 | 0.42 | -0.10 | 5 | 5 |
| P4 | 0.38 | -0.08 | 5 | 5 |

每个位置复用同一 Gazebo、MoveIt 和任务节点，试验之间重建场景并再次发开始请求，验证连续运行的状态清理。不同位置重新启动独立仿真进程。

一次通过必须同时满足：

1. 状态到达 `COMPLETE`，包括释放、退出和回待机。
2. Gazebo 实际物体最高点比初始中心高至少 5 cm。
3. 实际最终中心距放置区目标小于 3 cm。
4. 最终 6 个机械臂关节距 zero 的最大误差小于 0.02 rad。
5. 控制权归执行器期间未收到非零 Servo jog。
6. 最终物体竖直倾角小于 10°。
7. 控制权已释放，视觉控制器回到 `IDLE`，等待新的开始请求。

观察 `/gazebo/model_states` 的实际模型位置，既不以跟随指令值作为结果，也不以一句完成日志作为结果。每次保存起点、终点、最高高度、耗时、状态变化和失败原因。

最终批次 `acceptance-03` **40/40 通过**。每种物品均覆盖上述 4 个位置，每个位置连续 5 次；全部有控制权领取和释放记录，领取期间非零 Servo jog 数为 0。

| 对象 | 完整取放通过 | 单次耗时范围 | 实际最大抬升的范围 | 最大放置误差 | 最大回零关节误差 |
| --- | --- | --- | --- | --- | --- |
| 小球 | 20/20 | 41.45–54.65 s | 12.00–13.29 cm | 0.012 mm | 0.000099 rad |
| 实心圆柱体 | 20/20 | 44.19–69.96 s | 12.00–13.13 cm | 0.012 mm | 0.000108 rad |

这些极小的放置误差来自强制位置跟随的仿真模型，**不能解读为机械臂的实际定位精度**。40 次通过仅适用于当前两种模型、四个静态起点及这组参数，不是物理抓取成功率或全工作空间保证。

构建：7 个包通过。算法测试：45 个 GTest 用例、6 个 CTest 目标通过；colcon 汇总为 51 项，0 失败、0 跳过。新增用例覆盖实测静止判断、失效反馈以及中间腕部绕转拒绝。

证据：[逐次汇总 JSON](../simulation/validation/step1/acceptance-03/summary.json)、[CSV](../simulation/validation/step1/acceptance-03/summary.csv)、[指标汇总](../simulation/validation/step1/acceptance_metrics.json)、[构建日志](../simulation/validation/step1/build_final.log)、[测试汇总](../simulation/validation/step1/unit_test_summary.txt)。每个汇总条目都指向相应 `trial_XX.json`，所在目录还保存控制器、视觉、执行器及 Gazebo 原日志。

### 4.2 失败处理验收

普通停止和急停在接近阶段注入；目标消失通过停止检测器注入；无解用例把 MoveIt 目标坐标向 x 方向偏移 2 m，Gazebo 物体保留在原处。停止结果观察随后 2 s 的实测位置样本：前 0.5 s 用于收敛，之后至少覆盖 1 s 的连续反馈，按相邻样本计算的最大速度须小于 0.02 rad/s，且末次反馈不超过 0.25 s。不能只比较首尾坐标，也不使用已知会残留的速度字段。该检查不等于验证急停响应小于 50 ms。

| 场景 | 结果 | 观察到的处理 |
| --- | --- | --- |
| 接近时普通停止 | 通过 | `STOPPED / USER_STOP`；停止服务确认成功，物品未抬起；稳定反馈覆盖约 1.50 s |
| 接近时外部急停 | 通过 | `FAULT / EOG_OR_EXTERNAL_EMERGENCY_STOP`；物品未抬起；稳定反馈覆盖约 1.50 s |
| 搜索中检测器断流 | 通过 | 达到恢复上限后 `FAULT / RECOVERY_LIMIT_REACHED`；未闭合抓取或抬起，末段最大实测推算速度约 0.000001 rad/s |

这三项使用视觉入口，结果保存在[视觉失败处理记录](../simulation/validation/step1/visual_failure_checks.json)，原始数据分别位于 `negative-stop-final`、`negative-estop-final`、`negative-target-loss-final`。

另外，无解目标注入对照在取消固定坐标任务时已结束，得到 `FAULT_DIAGONAL_SIDE_PREGRASP_PLAN_FAILED` 且物品未抬起，作为辅助诊断保留。**按用户要求，不再追加固定坐标正向验收**；已排队启动的 `cup-known-final` 在放置下降阶段中断并清理，属于取消的试验，不计作运行失败或成功。范围调整见[记录](../simulation/validation/step1/scope_update.json)。

## 5. 如何复现

### 5.1 无窗口自动验收

**本节原有命令不会弹出 Gazebo 或 RViz 窗口**，只能查看终端状态和保存的结果。想直接看到机械臂抓取，请使用下面的 **5.2 单终端操作**。

下面的程序会启动无窗口 Gazebo、MoveIt、模拟控制器和检测/任务节点，并让虚拟机械臂执行动作。结束后仅清理它自己启动的进程组。加载仿真 overlay 即可，不要加载真实机器人 overlay。

```bash
cd /home/young1x/robot_projects/piper_robot/simulation
source /opt/ros/humble/setup.bash
source install/setup.bash

# 每次输出目录必须不存在；换一个新目录名即可重跑。
python3 -s scripts/validate_sim_grasp.py ball --output validation/my-ball-run
python3 -s scripts/validate_sim_grasp.py cup-vision --output validation/my-cup-run

# 同一位置连续运行 5 次。
python3 -s scripts/validate_sim_grasp.py ball --repetitions 5 --output validation/my-repeat-run

# 按预先规定的 40 次计划运行，任一失败就停下并保留结果。
python3 -s scripts/run_step1_trials.py \
  --plan validation/step1/trial_plan_final.json --output validation/my-acceptance-run
```

`python3 -s` 使用系统 Python 包，避免本机用户目录 NumPy 2 与 ROS cv_bridge/NumPy 1 的兼容冲突。验证脚本的第一帧图像用 Pillow 保存，没有依赖 cv_bridge 的 Python 转换。

后续开发与验收以 `ball`、`cup-vision` 两个相机入口为主；固定坐标入口只保留为诊断代码，不再追加该类正向试验。视觉入口的抓取 x/y 来自每次相机观测，四个预置场景位置是重复试验样本，并不是执行器写死的抓取坐标。当前放置区仍固定，抓取高度还依赖已知模型/桌面；这些限制需要后续解除。

本步只验证静态物品。锁定目标模型后的短暂视觉遮挡不会重新追踪；尚未验证抓取过程中物品移动或真正被删除的处理。检测断流用例在搜索/居中阶段注入，不能外推为所有阶段的目标消失测试。起点邻域检查也只是有限扰动测试，不是全工作空间的数学鲁棒性证明。

### 5.2 推荐：一个终端，按键完成整套可视化仿真

现在可以使用两个专用入口，**不用手动 source 环境，不用开启多个终端，不用逐个启动 ROS 节点，也不用手动添加相机图像**。程序会自动加载 Gazebo、MoveIt、RViz、桌面/物品、腕部 RGB-D 相机、检测器和视觉取放任务。加载完只等待按键，不会自动开始运动。

在 Ubuntu 图形桌面打开一个终端，任选一种物品运行；两个入口共用实例锁，一次只运行一个。

**抓取小球：**

```bash
cd /home/young1x/robot_projects/piper_robot/simulation
./scripts/run_ball_visual_sim.sh
```

**抓取圆柱体：**

```bash
cd /home/young1x/robot_projects/piper_robot/simulation
./scripts/run_cylinder_visual_sim.sh
```

本机已构建当前版本，可以直接使用，无需安装依赖。后续新增的随机取放更改了抓取执行器，其他电脑更新源码后需按仿真 README 构建。也可以从任意目录调用上述脚本的绝对路径。

等待终端显示 `[就绪]`，将键盘焦点留在启动程序的终端；按键**不用回车**，大小写均可：

| 按键 | 作用 | 什么时候按 |
| --- | --- | --- |
| `1` / `2` | 选择 A / B 放置区，RViz 高亮选中区域 | 就绪时，在 S 之前 |
| `S` | 从相机搜索开始，自动完成抓取、搬运、释放、回零 | 首次就绪，或复位完成后 |
| `R` | 随机生成新起点，确认场景同步后允许下一轮 | 完整取放结束后 |
| `X` | 中止正在运行的视觉取放 | 想提前停止时 |
| `Q` | 停止任务并关闭本程序启动的全部仿真进程 | 任何阶段，包括加载时 |
| `Ctrl+C` | 退出并清理，效果同退出操作 | 不方便按 Q 时 |

常用操作顺序：

```text
运行脚本 → 等待“就绪” → 按 S → 在 Gazebo 看抓取
→ 等待“第 1 轮取放完成” → 按 R → 等待“复位完成”
→ 按 S 再抓一次 → 完成后按 R 继续，或按 Q 退出
```

正常完成时机械臂已经回零，`R` 随机生成新起点，以同一配置重载场景与跟随节点，并核对实际位置。**运行中按 R、1/2 会被拒绝，重复按 S 也不会启动重叠任务。** `X` 停止或出现故障后，再按 `R` 会自动重载整套仿真，清理中途的附着/跟随状态；窗口会重新打开，等待再次就绪即可。

窗口会自动显示：

- **Gazebo**：虚拟机械臂、桌面和物品的实际动作；可以调整视角。
- **RViz**：中间为机器人和碰撞场景，右侧为 `Wrist Camera` 原图与 `Target Detection` 检测图。它只显示场景，不提供运动操作面板；控制操作集中在终端按键。
- **终端**：加载进度、关键视觉/抓取阶段、完成或故障原因。初始视野没有目标时出现 `TARGET LOST` 并不代表启动失败；按 S 后会先进入观测姿态。

详细日志自动保存在 `simulation/log/visual_sim/<物品-时间>/`，路径会在启动时打印。`events.jsonl` 保存按键操作和状态变化，`session.json` 保存完成轮次和实际物品/关节结果，各组件日志按重载次数编号。退出仅回收本程序创建的进程组，不清理其他仿真实例。

本入口采用独立 ROS 域 83 和 Gazebo 端口 11483，自动配置本地通信；不启动真实驱动。RViz 使用进程内的软件 OpenGL 配置解决本机图像面板的渲染问题，不改变系统显卡驱动或桌面配置。关闭观察窗口也会结束本会话；推荐在终端按 Q 统一退出。

开发检查可使用 `--headless` 隐藏窗口，按键和任务逻辑保持相同；正常观看时不需要此参数。

**随机功能加入前的入口检查结果（历史记录）：** 小球完成 2 轮连续取放；圆柱体完成 2 轮连续取放，另在中途停止、R 重载后再次完成 1 轮。运行中复位、重复开始、并行启动另一个实例均被拒绝；小球用 Q 退出、圆柱体用 Ctrl+C 退出，退出码均为 0，未残留本次 Gazebo/MoveIt/RViz/任务进程。实际抬升、最终放置和回零检查通过；这些是新增入口的 GUI 检查，不混入原 40 次验收。

结果与日志路径见[单终端入口验证记录](../simulation/validation/visual_console/validation.json)。初版 RViz GLX 渲染崩溃日志保留，修复后使用独立监控的 RViz 进程、PlanningScene 显示和进程内 Mesa 渲染；没有安装或替换系统依赖。真实工作区 334 个导入文件仍未变化，当时原抓取执行器二进制哈希保持不变；后续随机取放更新了执行器，见下方新报告。

### 5.3 多终端调试：先看小球抓取

这套操作会打开 **Gazebo 三维窗口和 RViz**，并启动与验收相同的虚拟机械臂、RGB-D 相机、控制器、检测器和视觉任务。发出开始请求后，虚拟机械臂会自行观察、搜索、接近、闭合、抬升、搬运、释放和回零。不会启动真实机械臂驱动。

在本机 Ubuntu 图形桌面操作。准备 **6 个终端**，按照编号启动；运行中的终端保持打开。先结束之前的自动验收或其他 Piper 仿真，避免同一组服务、控制器和 Gazebo 端口冲突。一次只演示一种物品。

**每个新终端都先执行这一段公共配置**，然后再执行该终端的命令：

```bash
cd /home/young1x/robot_projects/piper_robot/simulation
export PYTHONNOUSERSITE=1
source /opt/ros/humble/setup.bash
source install/setup.bash
export ROS_DOMAIN_ID=82
export ROS_LOCALHOST_ONLY=1
export GAZEBO_MASTER_URI=http://127.0.0.1:11482
export FASTRTPS_DEFAULT_PROFILES_FILE="$PWD/validation/fastdds_local_udp.xml"
export RMW_FASTRTPS_PUBLICATION_MODE=ASYNCHRONOUS
```

所有终端必须使用相同配置。`PYTHONNOUSERSITE=1` 避免用户目录中的 NumPy 冲突；DDS 配置只作用于这些进程。已有构建可以直接使用，本次操作不需要安装依赖。

#### 终端 1：打开 Gazebo 和虚拟机械臂

```bash
ros2 launch brain_robot_pick_place wrist_camera_gazebo.launch.py \
  gui:=true start_raw_viewer:=false \
  world:="$PWD/validation/grasp_validation.world"
```

应弹出 Gazebo 窗口并出现 Piper 模型。等待终端输出：

```text
All four Gazebo controllers active; retaining service clients.
```

这表示关节反馈、机械臂和两个夹爪控制器已就绪。保持 Gazebo **运行而非暂停**；此时尚未创建物品，机械臂也不会开始抓取。

#### 终端 2：打开 MoveIt 和 RViz

```bash
ros2 launch piper_with_gripper_moveit piper_moveit.launch.py start_rviz:=true
```

应弹出 RViz。等待终端出现 `You can start planning now!`，再启动场景。RViz 的 `Fixed Frame` 应为 `world`，`MotionPlanning` 显示项应启用。

#### 终端 3：创建小球场景

```bash
ros2 launch brain_robot_ball_pick ball_scene.launch.py
```

等待 `Red ball scene ready: Gazebo and MoveIt are synchronized.`。Gazebo 中应出现桌面和红色小球，RViz 中会出现对应碰撞场景。调整 Gazebo 视角，让机械臂夹爪、红球及桌面的另一侧放置区都在视野内。

#### 终端 4：启动相机检测

```bash
ros2 launch brain_robot_ball_pick ball_detector.launch.py
```

检测器使用虚拟腕部相机的彩色图、深度图和相机内参。它本身不发机械臂运动指令。按 **5.4** 在 RViz 添加相机画面后，再开始抓取，方便观察目标如何被找到。

#### 终端 5：启动视觉搜索和取放任务

```bash
ros2 launch brain_robot_ball_pick ball_visual_search.launch.py backend:=simulation
```

这个入口会一起启动 Servo、视觉控制器和抓取执行器。等待控制器提示 `auto motion disabled until ~/start is called`。机械臂等待开始请求。

#### 终端 6：确认就绪并开始抓取

先检查控制器：

```bash
ros2 control list_controllers
```

应看到 `joint_state_broadcaster`、`arm_controller`、`gripper_controller`、`gripper8_controller` 四项均为 `active`。然后读取当前视觉状态：

```bash
ros2 topic echo /brain_robot_visual_control/state --once --qos-durability transient_local
```

首次开始前应为 `data: IDLE`。准备好观察窗口后，发出一次开始请求：

```bash
ros2 service call /visual_search_controller/start std_srvs/srv/Trigger '{}'
```

返回应包含 `success: true`。机械臂随即移动到观测姿态，再自动搜索、居中和取放；不需要额外触发抓取。若仅提示 `No fresh joint state`，确认 Gazebo 正在运行和四个控制器已激活，等约 2 秒再发一次开始请求。其他拒绝或故障原因先按 **5.6** 排查，不要持续重复发送开始请求。

开始后可在同一终端查看抓取阶段：

```bash
ros2 topic echo /brain_robot_grasp/state --qos-durability transient_local
```

此命令持续占用终端。要发停止或重置请求，先按 `Ctrl+C` 退出这个状态查看命令；这只停止查看，不停止机械臂。

### 5.4 在窗口里应该看什么

**Gazebo：观察虚拟机械臂和物品的实际动作。** 把视角对准桌面，依次应看到机械臂进入观测姿态、调整末端位置、斜侧接近红球、闭合夹爪、抬升约 12 cm、搬到另一侧、下降释放、向上退出和回零。观察期间只调整视角，运动由开始/停止服务控制；保持仿真运行。

**RViz：观察机器人状态、碰撞场景和相机画面。** 在 `MotionPlanning` 中观察 `Scene Robot` 与 `Scene Geometry`；`Planned Path` 可能循环播放规划预览，可关闭其中的 `Loop Animation`。以 Gazebo 动作和抓取状态确认一次任务的进度。

在 RViz 左侧 `Displays` 面板中点击 `Add`，选择 `Image`，添加两个图像显示项：

| 图像显示项 | Topic / Image Topic | 用途 |
| --- | --- | --- |
| 腕部相机原图 | `/wrist_camera/wrist_camera/image_raw` | 看机械臂末端相机实际拍到了什么 |
| 目标检测画面 | `/brain_robot_vision/debug_image` | 看检测框、目标中心、画面中心与定位状态 |

图像传输选择 `raw`。若有 QoS 不兼容提示，可将图像订阅的 `Reliability Policy` 设置为 `Best Effort`。两个显示项可能出现在独立图像面板中，可拖动布局，放在三维视图旁边。

开始前相机尚未进入观测姿态，画面中可能没有红球或显示 `TARGET LOST`；先确认图像持续更新即可。开始后观察画面如何变化、目标如何居中；接近和闭合时夹爪遮挡相机可能出现目标丢失提示，当前流程在锁定目标后不会持续重定位。

| 状态 | 画面中的对应动作 |
| --- | --- |
| 视觉 `PREPARE` → `SEARCH` → `ALIGN` → `GRASP_READY` | 进入观测姿态、找目标、居中、准备交接 |
| `DIAGONAL_SIDE_PREGRASP_PLANNING` / `DIAGONAL_SIDE_APPROACH_EXECUTING` | 选择抓取方向并接近 |
| `CLOSING_GRIPPER` / `VERIFYING_GRASP_CONTACT` | 闭合并进行几何位置检查 |
| `LIFTING` / `TRANSFERRING` | 抬起并搬到放置区 |
| `RELEASE_LOWERING` / `RELEASE_RETREATING` | 下降释放并退出 |
| `RETURNING_HOME` / `COMPLETE` | 回零并结束，视觉控制器随后回到 `IDLE` |

规划阶段可能静止等待数秒，这是候选筛选过程。验收中的单次取放约为 40–70 秒；图形渲染负载可能增加耗时。画面中的物品仍通过跟随机制搬运，几何位置检查不是力反馈。

### 5.5 再抓一次，或切换圆柱体

**同一种物品再抓一次：** 等到抓取 `COMPLETE` 且视觉状态回到 `IDLE`，在终端 6 重建小球场景：

```bash
ros2 service call /brain_robot_ball_pick/reset_scene std_srvs/srv/Trigger '{}'
```

返回成功只表示重置请求已排队。等待终端 3 再次输出场景就绪，确认 Gazebo 中红球已回到起始位置，再调用 `/visual_search_controller/start`。运动过程中不要重建场景。

**切换圆柱体：** 先按 5.6 结束当前仿真，再从 5.3 重新启动。公共配置及终端 1、2、6 的步骤相同，只替换终端 3、4、5 的命令：

| 终端 | 圆柱体的启动命令 |
| --- | --- |
| 3：场景 | `ros2 launch brain_robot_pick_place scene.launch.py` |
| 4：检测器 | `ros2 launch brain_robot_pick_place cup_detector.launch.py` |
| 5：视觉任务 | `ros2 launch brain_robot_pick_place visual_search.launch.py backend:=simulation` |

代码中的 `cup` / `medicine_cup` 对应当前实心圆柱体。相机图像话题、视觉开始服务和抓取状态话题保持相同。重复圆柱体取放时，重置服务换为：

```bash
ros2 service call /brain_robot_pick_place/reset_scene std_srvs/srv/Trigger '{}'
```

### 5.6 停止、退出与常见问题

**停止当前任务：** 在执行过公共配置的空闲终端中调用：

```bash
ros2 service call /visual_search_controller/stop std_srvs/srv/Trigger '{}'
```

视觉控制器应进入 `STOPPED`，执行器中止当前运动。途中停止不等于完整取放；物品可能停在途中。要重新演示，建议退出本轮各进程后按 5.3 重新启动。

**退出整套仿真：** 停止任务后，在终端 5、4、3、2、1 依次按 `Ctrl+C`，等待各启动命令退出。终端 6 若正在查看状态，也按 `Ctrl+C` 退出查看。不要只关窗口而让后台启动终端继续运行。

| 现象 | 先检查什么 |
| --- | --- |
| 没有 Gazebo / RViz 窗口 | 是否在本机图形桌面运行；`echo "$DISPLAY"` 是否非空；启动参数是否分别为 `gui:=true`、`start_rviz:=true` |
| 机械臂不动、状态停在等待 | 是否发过视觉开始请求、返回是否成功；Gazebo 是否暂停；四个控制器是否全部 `active` |
| Gazebo 有机械臂但没有物品 | 终端 3 是否启动并提示场景就绪；终端 2 的 MoveIt 是否已就绪 |
| RViz 看不到机器人或桌面 | `Fixed Frame` 是否为 `world`，`MotionPlanning` 是否启用；终端 2 是否有报错 |
| 图像一直不更新 | 检查两个图像话题是否存在、终端 4 是否仍运行、订阅 QoS 是否兼容，以及 Gazebo 是否暂停 |
| 开始请求一直等待服务 | 终端 5 是否仍运行；每个终端是否都执行了相同公共配置 |
| 状态出现 `FAULT` 或长时间无进展 | 在空闲终端执行下方原因查询，保存终端 5 的报错，停止任务后排查 |

```bash
ros2 topic echo /brain_robot_visual_control/reason --once --qos-durability transient_local
ros2 topic echo /brain_robot_grasp/state --once --qos-durability transient_local
```

多终端命令已与当前启动文件及 `ros2 launch ... --show-args` 核对。第 4 节的 40 次通过记录来自无窗口自动验收；第 5.2 节的新入口另外进行可视化启动、按键、复位与退出验证，结果单独记录，不混入原 40 次统计。
