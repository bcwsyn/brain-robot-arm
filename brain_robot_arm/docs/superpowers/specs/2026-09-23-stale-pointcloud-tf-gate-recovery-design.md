# Stale Pointcloud TF Gate Recovery Design

## Problem

The real-arm startup script can stop an old MoveIt/Servo visual stack, then
start a new one, while an old `pointcloud_tf_gate` or `robot_state_publisher`
process survives.  The gate publishes its diagnostic with transient-local
durability.  A new invocation of `ros2 topic echo` can therefore receive a
persisted `REJECTED` report from the old gate instead of a report generated by
the newly started gate.

Observed evidence distinguishes this from a current TF-chain failure:

- The persisted rejection requested transform time `1790139871.244317`, while
  current `/piper_moveit_joint_states` was stamped `1790143239`.
- A live `tf2_echo base_link link8` then returned successive current
  transforms.
- The startup script's stale-stack matcher does not include
  `pointcloud_tf_gate` or `robot_state_publisher`.

The failure makes startup abort before motion is authorized, despite a live
robot TF chain.

## Alternatives considered

1. Increase the TF lookup timeout or permit latest-time transforms.  Rejected:
   this weakens the point-cloud/robot time-alignment safety check and cannot
   distinguish an old diagnostic from a real timing failure.
2. Keep stale processes but ignore all rejected diagnostics.  Rejected:
   this would conceal a real missing-TF condition.
3. Terminate stale TF producers before launch and wait only for a fresh gate
   diagnostic.  Selected: it removes the source of stale state without
   changing transform acceptance requirements.

## Design

Only `scripts/start_brain_robot_cube_real.sh` changes.

1. Extend the stale visual-stack process identity matcher and its targeted
   fallback termination list to include the installed
   `brain_robot_pick_place/pointcloud_tf_gate` executable and the
   `robot_state_publisher` process belonging to the real visual-stack launch.
   The matcher remains path/identity based rather than DDS-discovery based.
2. In `wait_for_tf_validated_pointcloud`, subscribe with reliable, volatile
   QoS.  The pointcloud gate continually republishes diagnostics while clouds
   arrive, so a volatile one-shot subscriber receives only a post-subscription
   result, not a historical transient-local report.
3. Preserve existing gate behavior: success still requires
   `state=FORWARDED`; `REJECTED`, an absent message, or timeout still stops
   startup before Octomap use and before real-arm motion authorization.

## Scope and non-goals

This does not alter PiPER CAN configuration, arm-enable behavior, joint
commands, TF lookup timeout, required frames, point-cloud timestamps, or the
Octomap safety gate.  It does not attempt to repair a genuinely stale
robot-state publisher; it prevents one from surviving into the next launch.

## Validation

Static checks:

- shell syntax check of the startup script;
- verify stale-stack matcher and fallback contain both process identities;
- verify the diagnostic read uses volatile QoS and retains the exact
  `state=FORWARDED` acceptance rule.

Runtime acceptance:

1. Start after deliberately leaving an old visual stack running.
2. Confirm the cleanup reports the old stack exited.
3. Confirm a live `FORWARDED` diagnostic is received and startup passes step
   `[5/7]`.
4. Confirm a real missing-TF case still fails at `[5/7]` rather than starting
   the motion menu.
