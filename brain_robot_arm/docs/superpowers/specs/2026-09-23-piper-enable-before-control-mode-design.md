# PiPER Enable-Before-Control-Mode Design

## Problem

The V2 ROS driver currently sends `MotionCtrl_2` before the arm has completed
motor enable.  This happens in both the `/enable_srv` service path and the
`/enable_flag` topic callback.  On the physical PiPER running firmware
`S-V1.8-2`, this ordering can leave all motors disabled even though joint
feedback is healthy.

The physical test established the working sequence:

1. `GetArmJointMsgs()` reports fresh feedback at 200 Hz.
2. `EnablePiper()` completes with all six enable states true.
3. `MotionCtrl_2` selects CAN `MOVE_J` mode.
4. Repeated `JointCtrl` commands move J2 by 2.909 degrees and report successful
   target completion.

The official V2 joint-control example uses the same enable-before-mode order.

## Alternatives considered

1. Reorder only `/enable_srv`.  This fixes the one-command launcher but leaves
   the topic and automatic-enable paths inconsistent.
2. Centralize the ordered operation and use it from all enable entry points.
   Selected because it fixes the cause without changing motion parameters.
3. Retry `/enable_srv` from the launcher.  Rejected because retries preserve
   the incorrect ordering and can hide the driver defect.

## Design

Only the PiPER single-arm ROS driver changes.

Add a small helper that performs one non-blocking enable attempt:

1. Call `EnablePiper()`.
2. If it does not yet report success, return false without sending
   `MotionCtrl_2`.
3. Once all six motors are enabled, call `_set_joint_control_mode(50)` and
   return true.

The existing `/enable_srv` loop calls this helper until it succeeds or reaches
its existing timeout.  It reports `enable_response=True` only after enable and
mode selection both complete.  The `/enable_flag` callback and automatic
enable path use the same helper so all three entry points share the same
ordering.

The disable path remains unchanged.  No joint command is generated by the
helper, and gripper behavior is not broadened by this change.

## Safety and error handling

- A failed enable attempt cannot select motion mode or send a position target.
- Existing timeout behavior prevents an unbounded ROS service call.
- The driver continues to publish feedback while enable is being attempted.
- Firmware, master/slave role, CAN ID offsets, joint limits, speed settings,
  and collision checks are unchanged.

## Validation

Static validation:

- Python syntax compilation succeeds.
- Every enable entry point uses the common ordered helper.
- No direct `MotionCtrl_2` call occurs before the helper confirms enable.
- Disable logic remains unchanged.

Physical acceptance:

1. Start exactly one PiPER ROS driver.
2. Confirm `/joint_states` has fresh non-default feedback.
3. Call `/enable_srv` once and receive `enable_response=True`.
4. Confirm all six motors are enabled and `/arm_status` reports
   `ctrl_mode: 1`, `mode_feedback: 1`, and no error.
5. Run the protected visual stack and verify pressing `1` can leave zero reset
   and start the observation trajectory.
