# PiPER V2 ROS 驱动控制时序一致性设计

## 背景

干净断电并重新初始化 CAN 后，原始 ROS 驱动仍出现：`/enable_srv` 返回成功、`/joint_states` 持续发布，但 `/arm_status` 的 `ctrl_mode` 和 `motion_status` 均为 0，视觉控制器发出的非零 `/joint_commands` 没有导致真实关节反馈变化。因此问题已经排除为 SDK 示例进程残留，下一步需要修复 ROS 驱动与当前 PiPER V2 SDK/硬件的接口一致性。

仓库中的独立运动脚本使用 `C_PiperInterface_V2`，而 `piper_ctrl_single_node.py` 使用旧的 `C_PiperInterface`。本设计只调整底层 ROS 驱动适配，不改变视觉搜索、碰撞地图、抓取状态机或用户按键协议。

## 目标与非目标

目标：

1. 使用与当前 SDK 一致的 V2 PiPER 接口发送状态、使能和关节控制命令。
2. 将“电机使能”和“进入关节控制模式”分开验证，避免 `/enable_srv` 在控制模式仍为 0 时报告成功。
3. 保持现有 ROS 话题、服务名称、消息类型和启动脚本接口兼容。
4. 在控制状态未确认前阻止视觉控制器继续发送真实运动，并提供明确诊断。

非目标：

- 不修改视觉检测、对齐、点云、Octomap 或抓取规划。
- 不改变 Ctrl+C 才失能的用户流程。
- 不让启动流程自动执行未授权的真实运动。

## 设计

### 驱动接口

将 ROS 单臂节点的底层接口切换为 `C_PiperInterface_V2`，保留现有 ROS 外壳和回调。系统使用 `gs_usb` 外置 USB-CAN，因此 V2 接口必须以 `judge_flag=False` 创建，避免 SDK 按内置 CAN 设备的条件拒绝控制路径。V2 接口的单位换算、关节顺序和夹爪协议以仓库现有 V2 示例及 SDK 接口文档为准；任何换算变化必须通过状态回读验证后再保留。

### 使能与控制模式状态机

`/enable_srv true` 执行以下顺序：连接状态确认、PiPER 控制模式初始化、六轴使能、夹爪初始化、读取电机使能状态和控制模式状态。只有六轴使能成功且控制器报告可接受的关节控制状态，服务才返回成功并置位内部运动许可；否则返回失败，视觉层保持停止。

`/enable_srv false` 仍执行现有失能路径。视觉控制器和保护适配器的停止/失能边界不变。

### 关节命令路径

收到 `/joint_commands` 后，只有内部运动许可为真且底层状态仍有效时才发送 V2 `MotionCtrl_2` 与 `JointCtrl`。若反馈超时、CAN 状态丢失或控制模式退回 0，立即停止发送并发布可诊断原因，不主动调用 PiPER 失能，符合现有 Ctrl+C 约定。

### 兼容性与安全

所有现有 ROS 名称和参数保持不变，包括 `can_port`、`auto_enable`、`gripper_exist`、`/joint_states`、`/joint_commands` 和 `/enable_srv`。默认仍使用 `auto_enable:=false`，避免启动时无授权运动。

## 验证标准

1. 干净启动后 `/joint_states` 持续发布，且时间戳有效。
2. `/enable_srv true` 只有在六轴实际使能且控制模式有效时返回 `enable_response: true`。
3. 发送一个小幅、受限的 J2 测试目标后，`/joint_states` 能观察到对应反馈变化；测试完成后回到零点。
4. 未使能、控制模式无效或 CAN 丢失时，视觉控制器不会继续执行观测姿态运动。
5. 现有视觉节点、按键协议和 Ctrl+C 失能行为保持不变。

## 风险与限制

当前环境是 Windows 共享目录与 Ubuntu ROS 工作区分离，代码修改后必须重新同步并在 Ubuntu 中编译。真实运动验证必须在清空工作区、释放急停并确认机械臂处于非示教模式后进行；本设计不把编译成功等同于真实硬件验证成功。
